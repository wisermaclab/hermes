HERMES · mmWave FMCW radar simulator

HERMES simulation tutorial

This tutorial covers scene configuration, radar and solver settings, simulation execution, and measurement bundle preparation. It provides workflows for the browser GUI, command-line tools and Python APIs, with guidance on reproducing runs and comparing simulations with measured ADC data.

hermes-radar-sim 0.2.0 import name mmWaveRadar Commands run from the checkout root
Workflow summary
  • The GUI's Dynamic Scenes page and the headless CLI use the same experiment layer. New Python integrations should use simulate_human_room(HumanRoomSettings(...)). Save CLI run settings in a JSON configuration file.
  • Each interface uses common solver identifiers and parameter names: solvers rt, po and hybrid_po, and settings prefixed rt_, po_ or hybrid_ by the solver that reads them. Update cadences are counted in radar frames.
  • Notebook examples and the validation CLI call the solver engine directly and can use different defaults from the GUI. Align their configurations before comparing results (comparison table).
  • For GUI-equivalent experiments in Python, match the motion, scene, radar and solver settings with HumanRoomSettings (Python example).

System architecture

All interfaces use the same solver engine. The GUI and headless runner use an experiment layer that manages scene placement, radar construction, solver configuration, processed results and bundle export. Direct solver calls configure these inputs explicitly.

The GUI has two more pages. Static Target uses the same experiment implementation as simulate_static_target(settings) to compare RT and PO on a plate, a trihedral corner or an uploaded mesh; it has no CLI. Bundle Comparison opens exported runs and measured bundles and runs no solver of its own unless you ask for a fresh simulation.

Example configuration across interfaces

These examples configure Hybrid PO and RT for the bundled walking motion from 3.00 s to 3.15 s, with 64 chirps per radar frame. The window contains three radar frames. Match the scene, human placement, radar configuration and solver settings across interfaces before comparing outputs; their defaults can differ (default settings).

GUI

  1. Run hermes-gui and open Dynamic Scenes.
  2. Open Settings › Radar configuration, set chirps per frame to 64, then Apply.
  3. On Motion and scene, click Load default motion, then set Start [s] to 3.0 and End [s] to 3.15. The page reports 3 radar frames.
  4. Select Hybrid PO and RT, then click Start.
  5. When the run finishes, export the bundle ZIP.

Python

python

    HumanMotionSettings, HumanRoomSettings, HumanRoomSolverSettings,
    RadarSettings, simulate_human_room,

settings = HumanRoomSettings(
    motion=HumanMotionSettings(
        human_motion="data/AMASS/walking_poses_cmu_105_02.npz",

Simulation solvers

HERMES provides ray tracing (rt), physical optics (po) and hybrid physical optics (hybrid_po). The solvers use a common ADC cube layout, [frames, chirps, ADC samples, virtual channels], and support the same downstream DSP operations.

RT rt

Ray tracing (Sionna RT) of the whole scene with the human mesh in it. The scene is retraced at the start of every rt_refresh_frames radar frames; in between, each traced path follows the moving mesh and its geometry and phase are updated chirp by chirp. rt_refresh_frames=0 retraces every chirp.

Models
Room, human, every multipath up to the depth limit
Cost
One trace per refresh; with 0, one per chirp
Use for
Full-scene references; 0 for short windows
Settings
rt_*: rays, path cap, max depth, human bounces, refresh and visibility cadence, human diffuse coefficient

PO po

Physical optics on the human mesh alone. Walls, furniture, multipath and human–room coupling are left out. Exact integration runs every po_refresh_frames frames; in between, phase, delay and spreading follow the motion.

Models
Direct radar–body–radar return, facet by facet, with self-shadowing
Cost
Lowest of the human models
Use for
Isolating the body signature, micro-Doppler studies
Settings
po_*: integration mode, phase span, curvature tolerance, subdivision limits, refresh and visibility cadence

Hybrid PO rtpo

RT for the static room and PO for the moving human. Room paths are always blocked by the body, and up to four image-source reflectors couple the human with the room.

total = H_direct + E_static + H_env + E_human
Components
human_po, static_environment_blocked, human_env, env_human
Use for
Indoor scenes requiring both body returns and environment coupling
Settings
The rt_* settings for the room and blocking, the po_* settings for the body and coupling, and hybrid_*: coupling on/off, reflector cutoff and count, calibration

Common solver settings

Unprefixed settings apply to every solver.

tx_schedule
simultaneous (simultaneous transmission) or tdm (time-division transmission)
array_model
phase_center: solve once at the Tx and Rx array centers and add per-channel phase. subarray: solve once per pair of a Tx group and an Rx group, at the centers of the two groups.
array_tx_groups, array_rx_groups
Groups of zero-based antenna indices for subarray, numbered like selected_tx_indices; every active antenna in exactly one group. Empty means one group. One antenna per group is element-wise. Group antennas by spatial proximity; antenna index order does not always correspond to physical position.
Warning
PhaseCenterApproximationWarning when the aperture or a group is too large for the target range. The warning provides a suggested group count.

Hybrid PO calibrates by averaging single-human-only RT and human-only PO ADC powers over every chirp, virtual channel and ADC sample of the first simulated radar frame (hybrid_calibration="rt_first_pose") in each interface. It fits one amplitude gain, sqrt(P_rt_human / P_po_human), and reuses it for all frames and chirps of direct-human PO and both coupling orders; static-environment RT is unchanged. Set it to none for absolute PO amplitudes, which then do not depend on the ray budget, or to rt_sequence to fit over the whole window.

Solver update intervals

Cadences are counted in whole radar frames, because range–Doppler maps are formed per frame, and every update happens at a frame start. 0 means every chirp.

SettingWhat happens at the cadenceBetween updatesDefault
rt_refresh_framesFull ray traceTraced paths follow the moving mesh with coherent phase and delay updates1
rt_visibility_refresh_frames, rt_visibility_fade_framesKnown paths are re-tested for blocking by the body; blocked paths fade out over the fade length. Hybrid PO room blocking uses the same cadence.Blocking state is held1, 0
po_refresh_framesExact PO integration of every facet. Hybrid PO coupling uses the same cadence.Phase, delay and spreading follow the motion1
po_visibility_refresh_frames, po_visibility_fade_framesFacet self-occlusion is recomputed and fadedFacet visibility is held1, 0

Motion-dependent thresholds can trigger additional updates between scheduled refreshes. These updates supplement the frame schedule without replacing or resetting it.

TriggerFires whenDefaultWhere to set it
po_refresh_on_phase_error_radA facet's neglected phase change since its last exact solve, k × max|ΔL(vertex) − ΔL(centre)|, exceeds the threshold; that facet alone is re-integrated. L is the Tx–point–Rx path length; coupling uses its image-source Tx/Rx positions.0.1 radGUI, CLI, JSON, validation, Python
po_refresh_on_area_fractionA facet's relative area change since its last exact solve exceeds the threshold.0.30GUI, CLI, JSON, Python
po_refresh_on_normal_degA facet's normal changes by more than the threshold angle since its last exact solve.20°GUI, CLI, JSON, Python
rt_refresh_on_displacementAny vertex has moved more than this many metres since the last trace; the whole scene is retraced.offPython only

Measured on the tutorial walk (4 radar frames from 3.0 s, compared with an exact solve or retrace at every chirp):

  • PO accuracy in the evaluated window. The one-frame default is within 0.3% of exact PO at every chirp. Refreshing only every 4 frames is within 0.4% with the default 0.1 rad trigger, 0.2% at 0.03 rad, and 5% at 0.5 rad. It saves little time, because the trigger re-integrates about as many facets as the frame refresh would. The trigger does not cover visibility changes, which follow po_visibility_refresh_frames, so check long cadences on scenes where the body turns away from or towards the radar.
  • RT path coverage between retraces. Between retraces the path bank only updates the paths it has; a path that appears in between is missed until the next retrace. With specular paths only, retracing once per frame differs from retracing every chirp by 12–26% per frame, and retracing every 4 frames by up to 100% in one frame. A 5 mm displacement trigger fires at every frame start in this walk, so it recovers the once-per-frame result at the same cost. Keep rt_refresh_frames=1 unless you check longer cadences against retracing at every chirp.
  • Diffuse RT sampling variability. With diffuse scattering on (the GUI and CLI default), changing only the RT seed changes the RT ADC by about 100% at 100 000 rays per source, so compare RT cadences, or RT runs in general, with specular paths only or with far more rays.

GUI simulation workflow

The browser GUI supports scene preview, radar and solver configuration, simulation, and result inspection. Settings are stored in the browser; export a bundle to preserve the inputs and outputs of a completed run.

  1. Launch the GUI. The launcher binds to 127.0.0.1:5006, opens a browser tab and prints a per-launch password in the terminal.
    shell
    hermes-gui                 # --port 5007, --no-browser, --bundle run.zip
  2. Configure the radar and solvers in Settings. Settings has three tabs. Radar configuration covers the TI board, active Tx/Rx, the Tx schedule, FMCW waveform and antenna pattern. Solver settings has six groups: MIMO array, Physical optics, PO temporal cadence, Ray tracing, RT temporal cadence, and Hybrid PO (coupling, calibration and image-source reflectors). Motion coordinates maps the source file's axes and units. Edits are staged until Apply; Apply & rerun this page also starts the run.
  3. Set up the scene on Dynamic Scenes › Motion and scene. Click Load default motion for the bundled walk, or upload a motion NPZ. The default environment is Empty room; upload your own XML through Static environment scene (.xml, optional) (scene-file examples). Set human position, yaw, radar orientation and Diffuse (RT). Then choose the motion window with Start [s] and End [s], in seconds after the motion's first pose. The page shows how many radar frames fit in the window.
  4. Select solvers and start the simulation. Select any combination of RT, PO and Hybrid PO, then click Start. Stop cancels at the next safe point between solver steps.
  5. Inspect the results. Range profile, range–time and range–Doppler pages show all selected solvers together. Hybrid PO adds a shared-scale plot of its four components. Run metadata lists runtime, path and facet counts, and the slowest stages. Per-frame RT path and PO facet overlays are available on request.
  6. Export the simulation bundle. The export is a HERMES bundle ZIP with each solver's ADC as simulated_adc_<solver>.npz, sensor and frame metadata, scene inputs and an experiment_manifest_<solver>.json for each solver. Reopen it with hermes-gui --bundle run.zip.

GUI parameter coverage

PO visibility sampling and refresh thresholds are configurable under Settings → Solver settings. The GUI selects the compute backend automatically; use CLI --backend or Python compute_backend to select it explicitly. The optional RT displacement trigger is available through the Python solver API.

If you change a setting after a run, the plots stay up with a banner naming the change, and a dot marks the tab as stale. Exports are disabled until you rerun or revert.

Scene configuration

The scene XML describes the static environment: floor, walls, other fixed geometry and their radio materials. Supply the human motion or target mesh separately.

GUI scene selection

Open Dynamic Scenes → Motion and scene in the left controls, then choose an XML file with Static environment scene (.xml, optional). An uploaded XML takes precedence over Prepared scene fallback. Clear the upload to use that preset again. Scene uploads are available for locally bound GUI sessions.

Without an upload, the GUI starts with Empty room: no furniture, a metal floor and plasterboard walls. The radar is at (0, 0, 0) m and the floor surface is at z = −1.035 m, so the radar is 1035 mm above it. The standalone version is data/scenes/empty_room.xml (under public/ in the full workspace). Upload an edited copy to use your changes. Editing the standalone XML does not change the built-in preset, which is generated from tutorial_support.py; changes to that Python module require restarting the GUI.

For motion that already contains the subject's measured position, choose Human placement → Use motion-file coordinates. Coordinates are converted according to Settings → Motion coordinates. Choose Place manually to position the first pose's bounding-box centre yourself.

CLI and JSON scene configuration

Use --scene on the headless runner, or scene_xml in its JSON. For example, simulate an evaluated human mesh in the standalone empty room from the package checkout root:

shell
hermes-human-room \
  --motion /path/to/human_motion.npz \
  --scene data/scenes/empty_room.xml \
  --position 2.0 0.0 0.0 \
  --solvers po hybrid_po \
  --output /path/to/results/human-room.zip

A partial run config can specify the same scene and place the first pose's bounding-box centre at (2, 0, 0) m:

run.json · simulation configuration
{
  "schema_version": 3,
  "human_motion": "/path/to/human_motion.npz",
  "scene_xml": "/path/to/empty_room.xml",
  "human_position_m": [2.0, 0.0, 0.0],
  "solvers": ["po", "hybrid_po"],
  "output": "/path/to/results/human-room.zip"

shell

To select the built-in empty room instead of an XML, set "room_preset": "empty_room" and "scene_xml": null, or use --room-preset empty_room with no scene override. Keep scene and motion in the same world frame: metres, +X forward, +Y left and +Z up for an unrotated radar.

Scene keys by configuration type

A simulation run.json uses scene_xml. A measurement prepare.json uses scene. Both command-line tools accept --scene. Paths in JSON are relative to the JSON file; paths passed as flags are relative to the working directory.

The headless runner executes the Dynamic Scenes experiment workflow and exports a bundle ZIP. Use JSON configuration files and command-line overrides for repeatable runs and parameter sweeps.

Python APIs and notebooks

The experiment API provides grouped settings and processed results for scene-level simulations. The direct solver API provides control over scene construction, radar placement, targets and numerical settings, as demonstrated in the notebooks.

Experiment API with grouped settings

Use simulate_human_room(settings) or simulate_static_target(settings) for new Python code. Their settings declare motion or geometry, scene, radar and solver options separately. Matching those settings gives the same experiment results as the GUI or CLI.

python · human motion in the empty room
from dataclasses import replace
from mmWaveRadar.experiments import (
    HumanMotionSettings, HumanRoomSettings, HumanRoomSolverSettings,
    RadarSettings, RoomSceneSettings, simulate_human_room,
)

settings = HumanRoomSettings(
    motion=HumanMotionSettings(
        human_motion="/path/to/human_motion.npz",
        human_position_m=None,  # preserve motion-file coordinates
        motion_start_s=0.0,
        num_frames=2,
    ),
    scene=RoomSceneSettings(room_preset="empty_room"),
    radar=RadarSettings(num_chirps_per_frame=16),
    solver=HumanRoomSolverSettings(solver="po"),
)
result = simulate_human_room(settings)
next_settings = replace(settings, radar=replace(settings.radar, num_adc_samples=128))

To load a custom room, use RoomSceneSettings(scene_xml="/path/to/room.xml"). Settings are frozen containers; replace creates a changed setup while retaining arrays and scene objects by reference.

python · static metal plate
from mmWaveRadar.experiments import (
    StaticTargetGeometrySettings, StaticTargetSettings, simulate_static_target,
)

plate = StaticTargetSettings(
    target=StaticTargetGeometrySettings(
        target_type="plate", range_m=0.668, width_m=0.152, height_m=0.152,
        material_name="pec",
    ),
)
result = simulate_static_target(plate)

This uses the perfect-conductor plate preset. A measurement bundle can supply numeric copper material parameters, as described in bundle preparation.

The flat keyword functions remain supported for compatibility. Their JSON keys and flags are listed in the settings reference; grouped settings map to those keys through settings.as_keywords().

Compatibility example: load an existing CLI configuration in Python

This handles paths and keys as the CLI does and calls its flat compatibility entry point.

python · run a CLI config in a notebook
import json
from pathlib import Path

from mmWaveRadar.experiments import run_human_room_experiment

config_path = Path("configs/human_room.json").resolve()
config = json.loads(config_path.read_text())

# Paths in the JSON are relative to the JSON file, exactly as in the CLI.
for key in ("human_motion", "smpl_model_dir", "scene_xml"):
    if config[key] is not None:
        config[key] = str((config_path.parent / config[key]).resolve())

# Run-control keys belong to the CLI, not to the experiment API.
solvers = config.pop("solvers")
for key in ("schema_version", "output", "quiet", "force"):
    config.pop(key)

results = {
    solver: run_human_room_experiment(**config, solver=solver)
    for solver in solvers
}

Direct solver API

Direct solver calls accept an explicitly constructed scene, RadarSensor and MeshTarget. The notebooks demonstrate this workflow. The following example lists the solver settings used by the GUI experiment layer.

    po_quadrature_max_refinement_depth=3,

Measurement bundle preparation

Bundle preparation packages decoded measurement data and its simulation inputs into a checked, self-contained ZIP. It does not run a simulation.

Required inputs

  • ADC: a pickle-free NPZ containing numeric adc [F, M, N, C]: frames, chirps per TX, samples and virtual channels. Optional times [F, M] stores chirp timestamps. Decode recorder formats such as KVNL before this step.
  • Sensor: a sensor.json describing the actual board or array, channel order, active TX/RX, TX schedule and capture waveform. Use the TI IWR6843AOP metal-plate sensor example described below and the bundle specification for the fields. There is no universal default for measurement data; match the settings to your acquisition.
  • Environment: your room XML. For the GUI's empty room, copy data/scenes/empty_room.xml beside the measurement inputs. Keep the human or plate out of this XML, since simulation inserts the separately supplied target.
  • Human or target: an evaluated human motion NPZ with vertices [T, V, 3], integer faces [P, 3] and times [T], or a static target mesh with vertices [V, 3] and faces [P, 3]. Geometry must already be positioned in the scene's world coordinates, in metres.

Instead of --sensor sensor.json, you can supply --ti-config /path/to/radar.cfg --board-model IWR6843AOP when your TI configuration uses the supported waveform commands. Inspect the imported waveform and channel mapping against the capture.

TI IWR6843AOP sensor example: copper-plate experiment

Save examples/metal_plate_sensor.json as sensor.json beside your ADC. Its waveform values come from the copper-plate capture metadata, using the IWR6843AOP's three TX and four RX. The experiment used a 152 × 152 mm copper plate approximately 0.668 m from the radar; the plate geometry belongs in the target mesh, not in sensor.json.

The TX firing order, 50 ms frame period and I/Q/board-phase conventions remain assumptions for this capture, recorded in the example's metadata. Verify them for your acquisition. With that TDM order, the full TX cycle is 3 × 65 µs = 195 µs. For a human capture or a different waveform, update the sample/chirp counts and timing to match its ADC; do not reuse the plate's singleton chirp count for a multi-chirp recording.

Human motion in the empty room: direct arguments

This example assumes regular 50 ms radar frames starting at t = 0 on the motion archive's timeline. Replace those times with your capture's timing:

shell
mmwave-prepare-bundle \
  --adc /path/to/capture/radar_adc.npz \
  --sensor /path/to/capture/sensor.json \
  --scene /path/to/capture/empty_room.xml \
  --evaluated-mesh /path/to/capture/human_motion.npz \
  --motion-coordinate-frame world \
  --start-time-s 0 --frame-period-s 0.05 \
  --output /path/to/capture/human-bundle.zip

Preparation preserves the supplied human positions; it does not apply the GUI's manual placement or coordinate conversion. Explicit timing and --motion-coordinate-frame world are required whenever motion is supplied. For irregular frame starts, use --frames /path/to/frames.json or --frame-times-s 0 0.05 instead of the start/period pair, with one time per ADC frame. Frame times must share the motion timeline, including epoch times when applicable. Motion must cover the last physical chirp, not just the last frame start.

Simulation validation

Validation runs simulation against a bundle of measured ADC, radar configuration, frame timing and target geometry or body motion, and writes metrics and plots. Prepare your measurement bundle first; both ZIP files and bundle directories are accepted.

shell
mmwave-check-bundle /path/to/clip_bundle    # structure check, no simulation

python -m validation.cli \
  --clip /path/to/clip_bundle \
  --out /tmp/hermes_validation \
  --suite dsp_maps \
  --solvers po hybrid_po \
  --progress
  • --solvers takes the same names as everywhere else. The default is po rt.
  • Radar, waveform and timing come from the bundle. --rt-refresh-frames, --po-refresh-on-phase-error-rad, --hybrid-calibration, --no-rt-diffuse-reflection, --rt-refraction and --rt-human-specular-reflection set the solvers; other budgets stay at the simulator class defaults (see defaults).
  • --tx-indices and --rx-indices take zero-based indices, with ranges such as 0-2,9. Dataset and TI documents count antennas from 1, so their TX1 is index 0.
  • TDM bundles are simulated per Tx slot. --ignore-tdm-timing evaluates all selected Tx at the start of each cycle.
  • Pass --simulated-adc file.npz to score ADC you produced elsewhere, such as from a notebook, instead of simulating.

The bundle format is specified in BUNDLE_SPEC.md. Dataset adapters live in tools/bundle_prepare/.

Configuration considerations

Review these conventions when configuring a run or comparing results across interfaces.

  • Motion time and radar-frame indexing

    The GUI, CLI and JSON configuration select the motion window in seconds after the first pose. Radar frame 0 starts at the start time and the motion plays in real time, so Doppler follows the recorded speed for any frame period. Configuration files with schema_version 1 used pose-index begin_frame_index/end_frame_index windows, which stretched one pose interval over each radar frame. They are now rejected with conversion instructions. For pose index i in a motion recorded at R fps, use motion_start_s = i/R.

  • Frame-based update intervals

    rt_refresh_frames, po_refresh_frames and the visibility cadences update at frame starts. There is no sub-frame cadence: use 0 for every chirp. A one-frame run with a cadence of 1 therefore solves exactly once.

  • Configuration schemas and deprecated options

    Unsupported configuration schema versions, deprecated solver names such as coherent_rt, and flags such as --modes are rejected with migration instructions. Update existing files using the deprecated-name mappings.

  • Human placement and motion windows

    human_position_m places the bounding-box centre of the first pose in the file. If you start 3.0 s into a walk, the body begins wherever it has walked to by then. Move the position to compensate, or check the preview at the start time before running.

  • Board changes and explicit configuration values

    The checked-in JSON pins a 60 GHz carrier, Tx 0–2 and Rx 0–3. --board MMWCAS_RF_EVM then simulates the 76.8 GHz cascade layout at 60 GHz without an error. Use hermes-human-room --board …, which starts from defaults for that board, or also set --carrier-ghz, --tx-indices and --rx-indices. Check with --dry-run.

  • RT repeatability

    With diffuse scattering on, the default, the RT ADC at 100 000 rays per source changes by about 100% when only the seed changes. Even with the same seed, multithreaded runs differ by about 0.1%, because Dr.Jit's floating-point accumulation order varies. Compare RT results with specular paths only or many more rays. For bitwise checks, call drjit.set_thread_count(1) before running.

  • Antenna numbering

    HERMES uses zero-based antenna indices in the GUI, CLI, JSON, validation and Python APIs. TI's TX1 corresponds to index 0, and RX5 in one-based dataset notation corresponds to index 4. Deprecated one-based flags such as --tx, --rx, --subarray-tx and --subarray-rx are rejected.

  • Units and orientation conventions

    JSON uses SI units and flags use GUI units. Orientation is in degrees in the GUI, JSON and flags, and in radians in RadarSensor(orientation=…).

  • Relative path resolution

    Paths in JSON, including output, are relative to the JSON file. Paths in flags are relative to the working directory. The checked-in config writes to ../../results/, which is outside a standalone checkout, so pass --output.

  • Hybrid PO calibration

    Each interface fits one gain from human RT and human-only PO ADC powers averaged over the first simulated radar frame (hybrid_calibration="rt_first_pose"). This gain is reused for the whole run, so the human terms then depend on the ray budget. Set none for absolute PO amplitudes.

  • Phase-center approximation limits

    A wide array close to the target triggers PhaseCenterApproximationWarning, and the run records a phase_center_approximation event. Split the array with array_model="subarray" and the group counts the warning suggests, move the target farther away, or use fewer active elements. Each Tx-group/Rx-group pair is a separate solve, so run time grows with the number of pairs. Calibrated PO parts share one gain: rt_first_pose is refitted from all pairs' reference powers, and rt_sequence uses the first pair's fit.

  • Integration-dependent phase span

    Analytic modes default to 6 rad and quadrature to 1 rad. The CLI resets the span when you change the mode without setting it. In Python, pass po_quadrature_phase_span_scale_rad=None to get the mode's default.

  • Solver-specific parameters

    Parameter prefixes identify their scope: rt_* settings do not affect the PO solver, po_* settings do not affect the RT solver, and hybrid_* settings affect only Hybrid PO. The human diffuse coefficient affects only the RT solver. See the settings reference.

  • GUI parameter coverage

    The GUI exposes PO visibility sampling and refresh thresholds. Compute backend selection uses auto; select an explicit backend through the CLI or Python API.
